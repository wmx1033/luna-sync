# PRD：Insta360 多设备 NAS 自动备份服务

**状态：** 草案，待评审  
**产品名称：** Insta360 Sync  
**目标版本：** v2.0

## 1. 背景与问题

现有 Luna Sync 已能部署在 NAS / Linux Docker 环境中：连接相机 Wi‑Fi、扫描媒体、将新文件下载到本地，并提供浏览与预览界面。但相机通信逻辑目前集中在 `LunaClient`，其中包含 Luna Ultra 专有的认证字节、HTTP 地址和存储路径。

本项目将以现有 Luna Sync 为基础 fork 后独立演进。用户拥有 Luna Ultra、Ace Pro 2 和 GO Ultra，希望将 NAS 作为统一归档点：相机在家中开机并可通过 Wi‑Fi 连接时，NAS 自动发现、增量备份素材，无需每次手动导入手机或电脑。

## 2. 产品愿景

提供一个可通过 Docker Compose 部署在 NAS 上的本地优先备份服务。它能够管理多个相机配置，根据设备类型使用相应通信驱动，在相机可达时自动增量备份媒体，并给出清晰、可恢复、可审计的同步结果。

产品不依赖厂商云端，也不要求将照片/视频上传到第三方服务。

## 3. 目标与非目标

### 3.1 目标

1. 在 Linux / NAS 上以 Docker Compose 稳定运行；Windows 不属于 v2.0 范围。
2. 支持多个已配置 Insta360 设备，按设备串行自动备份。
3. v2.0 首发支持 Luna Ultra、Ace Pro 2、GO Ultra；三个驱动均须以真实设备完成协议验证和验收。
4. 对每个设备实现增量同步、断点续传、失败重试和同步记录。
5. 防止不同设备、不同存储来源、同名文件之间发生覆盖。
6. 提供中文优先的 WebUI，用于设备配置、同步状态、手动同步、媒体查看和日志排障；v2.0 的状态通知仅在 WebUI 中提供。
7. 已备份媒体始终保留在 NAS 本地；缩略图和转码缓存可独立清理。

### 3.2 非目标（v2.0）

1. 不控制相机拍摄、参数、固件或直播功能。
2. 不删除相机内文件；相机端清理需由用户在原生 App / 相机中完成。
3. 不实现云同步、跨 NAS 同步、团队权限、多用户账号或公网访问。
4. 不承诺所有 Insta360 历史型号通用；每个设备系列必须通过驱动适配与实机验证。
5. 不保证多台相机通过同一无线网卡并行同步。
6. 不支持没有可用无线网卡的 NAS 部署；v2.0 将 NAS 无线网卡作为自动同步的硬性前置条件。
7. 不构建、发布或验收 Windows 客户端；Windows 支持进入后续版本规划。

## 4. 用户与主要场景

### 4.1 目标用户

- 使用 Synology、QNAP、Unraid、TrueNAS 或 Linux 小主机的个人创作者。
- 有两台及以上 Insta360 相机，希望减少手机导入和手工整理。
- 重视本地存储、可恢复下载与素材归档结构的用户。

### 4.2 场景 A：回家后的自动备份

用户打开一台已配置相机并启用其 Wi‑Fi。NAS 在轮询周期中发现目标热点，连接后识别设备、扫描并仅下载未备份素材。完成后记录结果；如配置允许，NAS 恢复原先网络连接。

### 4.3 场景 B：手动指定设备同步

用户从 WebUI 选择 Ace Pro 2，点击“立即同步”。服务尝试连接该设备；若相机离线，界面展示明确原因并保留待同步状态，而非误报成功。

### 4.4 场景 C：中断后续传

同步中相机没电、离开热点范围或 NAS 重启。已下载数据保留为 `.part`；下次该设备重新可达时，服务验证远端文件并从已有字节位置恢复。

### 4.5 场景 D：多设备排队

Ace Pro 2 与 GO Ultra 均可发现时，服务按用户设定优先级或最近任务顺序逐台同步。一台设备连接期间，其余任务显示为等待，不发生同一无线网卡抢占连接。

## 5. 产品范围与版本计划

| 阶段 | 交付内容 | 成功条件 |
| --- | --- | --- |
| P0：基础重构 | 通用驱动接口、现有 Luna Ultra 逻辑迁移、设备注册与新的归档路径 | Luna Ultra 现有扫描/下载/预览能力回归通过 |
| P1：同步编排 | 多设备队列、状态持久化、失败重试、手动/定时同步、设备页 | NAS 重启后可恢复待执行任务与未完成下载 |
| P2：设备适配 | Ace Pro 2、GO Ultra 驱动及实机兼容验证 | 各设备均完成扫描、下载、续传的实机验收；作为 v2.0 首发范围 |
| P3：体验完善 | Webhook / 邮件 / NAS 通知、存储统计、导出诊断包 | 支持主动通知，用户可独立定位“相机离线 / 鉴权失败 / 空间不足” |

P0、P1 可以立即基于当前仓库推进。P2 需要用户提供对应设备，并在允许的本地网络环境中采集连接与文件访问行为；P0、P1、P2 共同构成 v2.0。

## 6. 功能需求

### 6.1 设备管理

- 用户可添加、编辑、禁用和删除设备配置。
- 每个设备至少包含：显示名、设备类型/驱动、SSID、密码（可选）、连接优先级、启用状态、归档根目录。
- UI 显示上次成功同步时间、最近错误、已备份文件数与待同步估计数量。
- 自动识别仅作为辅助：以 SSID、网关探测或驱动握手结果判断候选驱动；识别失败时不下载，提示用户选择驱动或提供诊断信息。
- 密码不出现在 API 响应、日志或页面回显中。

### 6.2 同步策略

- 支持“自动同步开启/关闭”“立即同步”“仅扫描不下载”。
- 默认间隔为 30 秒，最低 10 秒；对连续失败的设备使用退避，避免频繁切换 Wi‑Fi。
- 默认同步所有可枚举的媒体与伴随文件，包括照片、视频、LRV、RAW 及设备导出的元数据文件；WebUI 可展示其类型和体积。
- 默认增量策略：远端媒体的稳定 ID 未在同步清单中成功记录，且本地最终文件不存在时下载。
- 不以文件名作为跨设备唯一标识；稳定 ID 由 `device_id + storage_id + remote_path` 组成。
- 同步成功仅在文件完整、已原子改名且元数据已持久化后记录。

### 6.3 文件归档与命名

默认目录：

```text
{download_root}/
  {device_slug}-{device_serial_or_id}/
    {YYYY}/{MM}/{DD}/
      {storage}/
        {original_filename}
```

- 若设备或驱动无法获得拍摄日期，放入 `unknown-date/{storage}/`。
- 相同目标路径但内容不一致时，不覆盖现有文件；生成确定性的冲突后缀并记录告警。
- v2.0 不改写原文件名，不进行转码，不把缩略图与正式媒体混放。

### 6.4 下载与完整性

- 所有下载写入最终文件同目录的 `.part` 文件。
- 支持 HTTP Range 的驱动必须使用断点续传；不支持 Range 的驱动在检测到部分文件后从头重试，并在界面注明。
- 下载进度至少包括已下载字节、远端总字节、瞬时速度与当前文件。
- 下载完成后以远端内容长度校验；支持时额外使用设备提供的校验和。
- 相机掉线、超时或取消时保留 `.part`，并记录为“可恢复”。

### 6.5 Wi‑Fi 与连接调度

- 复用现有 `networkmanager`、`wpa_supplicant` 和 `none` 后端。
- `none` 模式下服务不改动网络，只要目标相机 IP 可达即可同步；适合路由桥接或用户手工连接。
- NAS 必须配备可由容器访问并控制的无线网卡；单无线网卡默认只允许一个“需要切换热点”的设备连接任务运行。
- 可选配置“同步完成后恢复原网络”；无法可靠恢复时必须提示用户而非静默切换。
- 若 NAS 有多块可用无线网卡，后续版本可增加接口绑定；v2.0 不承诺并行任务。

### 6.6 媒体库与预览

- 保留现有本地媒体网格/表格、过滤、搜索、删除和缓存清理能力。
- 本地媒体展示设备名称、拍摄时间、来源存储、下载完成时间。
- 缩略图与兼容预览仅属于缓存，可重建；清理缓存不得影响已备份原文件。
- 预览或缩略图失败不能影响同步任务结果。

### 6.7 状态、日志与诊断

- 设备状态：`disabled`、`idle`、`waiting`、`connecting`、`scanning`、`syncing`、`success`、`partial`、`error`。
- 每次同步生成任务记录：设备、开始/结束时间、扫描数、新增数、跳过数、下载字节、失败文件和错误摘要。
- 保留最近 200 条用户可见日志；完整结构化任务记录保留至少 90 天或由用户配置。
- 提供“导出诊断信息”：版本、配置中已脱敏字段、Wi‑Fi 后端、设备任务记录与日志；不包含密码、媒体内容或访问令牌。

## 7. 驱动架构

### 7.1 接口

每个设备驱动实现同一抽象接口：

```python
class CameraDriver:
    id: str
    display_name: str

    def probe(self, connection) -> ProbeResult: ...
    def connect(self, connection) -> None: ...
    def list_media(self) -> list[RemoteMedia]: ...
    def open_download(self, media, offset: int = 0) -> DownloadStream: ...
    def close(self) -> None: ...
```

`RemoteMedia` 统一包含稳定远端 ID、原始文件名、存储来源、拍摄时间、大小、类型、可选校验和与下载能力。驱动不得直接修改同步队列、归档路径或 Web 状态。

### 7.2 初始驱动

| 驱动 | 初始状态 | 备注 |
| --- | --- | --- |
| `luna_ultra` | 可迁移 | 基于现有固定 TCP 认证和 HTTP 文件目录实现 |
| `ace_pro_2` | 待实机验证 | 单独验证发现、鉴权、媒体清单、Range 下载和元数据 |
| `go_ultra` | 待实机验证 | 单独验证存储结构、连接流程和媒体格式 |
| `generic_http_index` | 可选 | 仅适用于无认证且目录索引兼容的设备，不作为官方兼容承诺 |

不能因品牌相同而共享 Luna Ultra 的认证数据或目录路径。驱动的实现与测试必须来自用户自有设备或公开、授权的协议资料。

## 8. 数据与安全

- 配置、同步数据库、缓存与下载目录分离挂载。
- Wi‑Fi 密码使用最小权限文件保存；Docker 环境下配置目录权限建议为仅运行用户可读写。
- WebUI 默认只面向可信局域网；v2.0 不内建账号系统。对外暴露前应通过 NAS 反向代理 / VPN / 访问控制保护。
- 文件删除只删除 NAS 本地副本；所有删除操作需二次确认，并在日志中记录。
- 不上传媒体、缩略图、设备密码或日志到外部服务。

## 9. 技术方案

### 9.1 推荐模块拆分

```text
app/
  drivers/              # 每台/每类设备的通信实现
  camera_driver.py      # 抽象接口与统一数据模型
  device_registry.py    # 设备配置、驱动选择、探测
  sync_engine.py        # 增量判断、队列、重试、持久化
  downloader.py         # 通用续传写入器（保留并扩展）
  wifi.py               # 复用现有 Wi‑Fi 后端
  media_library.py      # 本地媒体与缓存
  web_app.py            # API 与页面
```

### 9.2 持久化

建议从单个 JSON 设置文件演进到 SQLite：

- `devices`：设备配置与可公开状态；敏感字段可单独受限保存。
- `media`：远端稳定 ID、本地路径、大小、首次/最后同步时间、完成状态。
- `sync_runs`：任务运行记录。
- `sync_errors`：文件级错误与重试信息。

SQLite 适合单 NAS 服务的原子写入、索引查询与崩溃恢复，且无需额外数据库容器。

## 10. 关键交互

1. 首次启动：显示“添加相机”，提示选择驱动或自动探测。
2. 添加设备：填写名称、SSID、密码与自动同步策略；点击“测试连接”。
3. 测试成功：展示设备型号/标识、可扫描存储来源和媒体数量；用户确认后启用。
4. 首页：按设备卡片显示状态与最近同步结果；点击可查看任务详情、日志或“立即同步”。
5. 发生错误：展示可执行提示，例如“未发现热点”“相机认证失败”“NAS 磁盘空间不足”“此驱动不支持续传”。

## 11. 验收标准

### 11.1 通用

- Docker Compose 启动后，WebUI 可访问且不要求厂商云端。
- 相机离线时不创建空的最终文件，不把任务标记为成功。
- NAS 重启后，已完成记录不丢失，`.part` 文件可在后续同步继续下载。
- 同名文件来自不同设备或不同存储时均能保留。
- 清理缩略图/转码缓存后，原始备份文件数量和大小不变。

### 11.2 每个正式支持设备

- NAS 配备可用无线网卡时，可用已保存的 Wi‑Fi 配置连接并完成同步；在 `none` 模式下，也可对已可达的相机完成同步。
- 能扫描至少内置存储和/或设备实际可用的存储来源。
- 能下载照片和视频各至少一个。
- 在下载中断后能恢复或按驱动能力明确地安全重试。
- 相机再次同步时不重复下载已完成的同一远端媒体。
- 能对错误的密码、设备关机和存储卡缺失给出可读错误。

## 12. 风险与约束

| 风险 / 问题 | 影响 | 缓解方式 |
| --- | --- | --- |
| 各设备私有协议差异大 | 不能承诺快速通用支持 | 驱动隔离；逐设备实机验证后才标为支持 |
| NAS 单 Wi‑Fi 网卡会切走正常网络 | 影响家中网络可用性 | 支持 `none` 模式、独立无线网卡、完成后恢复网络 |
| 相机 AP 仅在开机时可发现 | 自动同步不具备即时性 | 定时扫描、手动“立即同步”、明确离线状态 |
| 大体积 8K 文件传输易中断 | 备份耗时且易产生残片 | Range 续传、`.part`、任务持久化、退避重试 |
| 厂商固件变更 | 已有驱动可能失效 | 记录驱动/固件兼容矩阵，保留原始诊断信息 |
| 本地 WebUI 无账号 | LAN 中可能被未授权访问 | 默认可信 LAN，部署文档要求反向代理/VPN 保护 |

## 13. 已确认的产品决策

1. 产品名称为 **Insta360 Sync**。
2. 本项目基于现有仓库 fork 后独立演进；v2.0 首发支持 Luna Ultra、Ace Pro 2、GO Ultra。
3. NAS 必须具备可用无线网卡；单网卡环境下设备同步串行执行。网络恢复策略作为实现阶段的部署配置确定。
4. 默认归档路径为“设备 / 年 / 月 / 日 / 存储 / 原文件名”。
5. v2.0 仅提供 WebUI 状态；Webhook、邮件与 NAS 通知进入 v3.0。
6. v2.0 默认同步 LRV、RAW、伴随元数据等大体积/附属文件。
7. v2.0 仅面向 Linux / NAS；Windows 支持延后至后续版本。

## 14. v2.0 实施路线与阶段目标

### M0：项目基线与开发环境

**阶段目标：** 从上游仓库 fork 出可独立维护的 Insta360 Sync，建立不破坏现有 Luna Ultra 能力的改造基线。

**任务包：**

1. 创建 fork、独立仓库说明与版本策略；将产品名称、容器镜像名、页面标题和示例配置改为 Insta360 Sync。
2. 固化本地开发、Docker / NAS 部署和测试命令；补充最小 CI，至少运行单元测试与 Python 语法检查。
3. 记录当前 Luna Ultra 的可用行为：连接、扫描、下载、取消、续传、预览与自动同步。
4. 设计并提交 v2.0 配置迁移方案：保留旧 `config.json` 的兼容读取，新增多设备配置入口。
5. 建立实机调试规范：仅使用自有设备；日志和抓包不记录 Wi‑Fi 密码、访问令牌或媒体内容。

**完成标准：**

- 现有测试全绿，Docker 镜像仍可启动。
- Luna Ultra 在旧配置下的核心同步流程不回归。
- 开发者可以在不连接实体相机时运行模拟 / 单元测试。

**依赖：** fork 权限、可运行 Docker 的开发机或 NAS。

---

### M1：多设备数据模型与持久化

**阶段目标：** 让系统能够可靠地保存多个相机、媒体记录和同步任务，替代目前单设备、内存为主的状态模型。

**任务包：**

1. 新增 SQLite 数据库及迁移初始化；数据库与下载目录、缓存目录分离。
2. 实现 `devices`、`media`、`sync_runs`、`sync_errors` 的数据访问层。
3. 定义设备配置模型：ID、名称、驱动类型、SSID、加密后的敏感连接信息、优先级、启用状态和归档根目录。
4. 定义统一 `RemoteMedia` 模型与稳定 ID：`device_id + storage_id + remote_path`。
5. 实现由旧单相机 JSON 配置到默认 Luna Ultra 设备记录的幂等迁移。
6. 增加数据库单元测试：重复运行迁移、同名跨设备文件、任务/错误记录和重启恢复。

**完成标准：**

- 可创建并列出多个设备，不同设备的同名文件不会冲突。
- 服务重启后，设备、已完成文件和任务历史仍然存在。
- 旧用户未修改配置也能生成一个可工作的 Luna Ultra 默认设备。

**依赖：** M0。

---

### M2：驱动框架与 Luna Ultra 迁移

**阶段目标：** 将现有 Luna 专有通信抽离为第一个标准驱动，确认新的抽象不会降低原有能力。

**任务包：**

1. 定义 `CameraDriver` 接口：`probe`、`connect`、`list_media`、`open_download`、`close` 及驱动能力描述。
2. 实现驱动注册表和按设备配置选择驱动的机制。
3. 将 `luna_client.py` 的 TCP 认证、内外置存储扫描、文件分类与大小探测迁入 `drivers/luna_ultra.py`。
4. 将相机网络连接与驱动通信分离：Wi‑Fi 模块只负责让目标地址可达，驱动只负责协议。
5. 为 Luna 目录解析、认证会话、稳定 ID 和下载流编写 mock 测试。
6. 用实机完成 Luna Ultra 的扫描、全量下载、断点恢复和视频预览回归。

**完成标准：**

- 原 `LunaClient` 不再被 Web 层直接调用。
- Luna Ultra 可在新的设备模型下完成与旧版本等价的同步。
- 驱动异常不会让后台 Web 服务整体退出，错误会落到设备任务记录。

**依赖：** M1、Luna Ultra 实机与 NAS 无线网卡。

---

### M3：同步引擎与单无线网卡调度

**阶段目标：** 建立驱动无关的同步编排，使多台相机可以安全排队、续传和恢复。

**任务包：**

1. 实现 `SyncEngine`：设备选择、连接、扫描、增量判定、下载、落库和结果汇总。
2. 把当前内存下载队列改成持久化任务队列；区分等待、连接中、扫描中、下载中、部分完成、成功和错误。
3. 实现单无线网卡互斥锁与按优先级的设备调度；禁止热点连接任务并发执行。
4. 实现重试与退避：区分相机离线、密码错误、协议错误、网络超时、空间不足和文件错误。
5. 对接通用 `downloader`，保留 `.part`、HTTP Range 续传和原子改名；按驱动能力处理不支持 Range 的设备。
6. 实现归档规则：`设备 / 年 / 月 / 日 / 存储 / 原文件名`，并处理未知日期与同路径冲突。
7. 实现启动恢复：重新调度未完成任务，识别已有完整文件和可续传的 `.part`。

**完成标准：**

- 两台模拟设备同时排队时，连接/下载按策略串行进行。
- 中断后重启服务，未完成文件能恢复，不重复下载已完成媒体。
- LRV、RAW、伴随元数据与常规照片/视频均进入同步范围。
- 每次同步均产生可查询的成功、跳过和错误统计。

**依赖：** M2；至少一块可由 Docker 容器控制的 NAS 无线网卡。

---

### M4：WebUI 与部署配置

**阶段目标：** 把多设备同步能力以可操作、可排障的方式交付给 NAS 用户。

**任务包：**

1. 新增设备管理页面：添加、编辑、禁用、删除、测试连接和立即同步。
2. 首页改为设备概览：状态、最近同步时间、文件数、下载字节、队列位置和最近错误。
3. 新增任务详情：扫描数、新增数、跳过数、失败文件、当前下载进度和日志。
4. 将本地媒体库接入设备、日期、媒体类型和关键词筛选；保留原有预览与缓存清理。
5. 更新 Docker Compose、配置示例和 NAS 部署文档，明确 `network_mode: host`、`privileged` 与无线网卡需求。
6. 对 API 增加输入校验；确保密码不回传、不写入用户可见日志。

**完成标准：**

- 用户不编辑 JSON 也可在 WebUI 添加和启用设备。
- 用户能区分“等待相机”“正在同步”“同步完成”“需处理错误”。
- 纯 WebUI 操作可完成一次 Luna Ultra 的配置、扫描和下载。

**依赖：** M3。

### M5：Ace Pro 2 驱动与实机验证

**阶段目标：** 将 Ace Pro 2 作为第二个正式支持设备交付。

**任务包：**

1. 在用户自有设备上记录 Wi‑Fi 发现、IP 分配、开放端口和官方 App 连接后的可观察行为。
2. 验证媒体清单来源、稳定远端 ID、存储来源、精确大小、日期与文件格式。
3. 验证下载是否需要鉴权、是否支持 Range、连接会话是否会过期。
4. 实现 `drivers/ace_pro_2.py`，不得复用未经验证的 Luna 认证数据或路径。
5. 为可脱离实机的协议解析、响应异常、续传能力和媒体分类编写测试。
6. 实机验收：首次同步、重复同步、下载中断、断点恢复、相机离线、存储卡缺失及视频预览。

**完成标准：**

- Ace Pro 2 在 WebUI 中可添加、测试连接并完成自动/手动同步。
- 至少各验证一条照片、视频和设备存在的附属文件；不支持的格式需明确展示而非丢失。
- 验收结果、测试固件版本和已知限制记录在兼容矩阵中。

**依赖：** M3、M4；Ace Pro 2 实机、可访问的 NAS 无线网卡。

### M6：GO Ultra 驱动与实机验证

**阶段目标：** 将 GO Ultra 作为第三个正式支持设备交付，并验证可更换存储介质场景。

**任务包：**

1. 按 M5 的调试规范确认 GO Ultra 的热点、地址、鉴权、媒体清单和下载协议。
2. 重点验证存储卡插拔、更换卡后媒体稳定 ID 与目录归档的行为。
3. 实现 `drivers/go_ultra.py`，将设备特有格式映射到通用媒体模型。
4. 验证所有可枚举附属文件均被默认纳入同步，不因未知扩展名被静默过滤。
5. 实机验收首次同步、重复同步、断点恢复、存储卡变化、相机离线与预览降级行为。
6. 更新兼容矩阵、部署文档和常见问题。

**完成标准：**

- GO Ultra 的增量同步不覆盖同名文件，不因更换存储卡误判为已备份。
- 设备的照片、视频和附属文件在 NAS 中按统一归档规则保存。
- Luna Ultra、Ace Pro 2、GO Ultra 连续排队同步回归通过。

**依赖：** M3、M4；GO Ultra 实机、可访问的 NAS 无线网卡。

### M7：v2.0 发布验收

**阶段目标：** 形成可供日常 NAS 使用的 v2.0 发布版本。

**任务包：**

1. 运行完整单元、集成与三台实机回归测试；修复 P0 / P1 缺陷。
2. 完成兼容矩阵：设备型号、已验证固件版本、Wi‑Fi 后端、可用存储来源、续传和预览能力。
3. 完成安装、升级、备份目录迁移、故障恢复和安全部署文档。
4. 检查容器权限、配置文件权限、日志脱敏及路径遍历防护。
5. 发布镜像、版本说明和已知限制；明确不支持的设备不会被标示为“通用兼容”。

**完成标准：**

- 三台目标设备均完成正式支持验收。
- 新用户可从 Docker Compose 完成安装、添加设备与首次同步。
- 升级用户可以保留旧下载目录并迁移到新的多设备状态库。
- 无阻断级安全或数据完整性问题。

**依赖：** M5、M6。

## 15. 推荐执行顺序与关键路径

```text
M0 基线
  → M1 数据模型
  → M2 Luna 驱动迁移
  → M3 同步引擎
  → M4 WebUI / 部署
  → M5 Ace Pro 2 驱动 ─┐
  → M6 GO Ultra 驱动 ──┼→ M7 v2.0 发布
                         ┘
```

M5 与 M6 在 M3、M4 完成后可以并行推进，但每个驱动都依赖对应实机可用。若设备调试受阻，通用架构和 Luna Ultra 不应停止；但 v2.0 发布门槛仍要求 Ace Pro 2 与 GO Ultra 达到验收标准。
